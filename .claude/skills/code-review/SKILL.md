# code-review

## 목적
규칙 기반의 일관된 코드 리뷰. 사람마다·시점마다 다른 즉흥 리뷰가 아니라 이 프로젝트의 `rules/`를 잣대로 삼는다.

## 범위 (사용자가 지정)
1. **단일 파일** — 경로 1개
2. **디렉토리** — 해당 디렉토리 내 코드 파일(재귀)
3. **전체 코드베이스** — repo 전체 (규모가 크면 레이어/모듈 단위로 분할 리뷰 제안)

범위가 모호하면 먼저 확인한다. 전체 리뷰는 토큰이 크므로 우선순위(핵심 경로·최근 변경분)부터 제안한다.

## 진입 전
- 해당 언어의 `rules/coding/_common.md` + 언어 파일, `rules/logging.md`를 먼저 읽어 기준을 로드한다.
- (백엔드 `coding/python.md`+`coding/fastapi.md` · React `coding/react.md` · 빌드 없는 화면 `coding/html-css.md`. 검사 관련 리뷰는 `rules/testing.md` 도.)

## 점검 항목 (rules 매핑)
- **구조/추상화**: 레이어 단방향 의존, SRP, 교체 지점 인터페이스화, 과잉 추상화 여부
- **타입/문서**: 타입 힌트(py: mypy strict / ts: strict, no any), Google docstring, public API 문서화
- **신뢰성**: 경계에서만 catch, 재시도 멱등성, silent 품질저하·설정 무시 없음, 부분 실패 판정선(다음 단계 입력 · 산출물에 실을 수 없는 변화)
- **로깅**: print/console 잔존, 레벨 적정성, 민감정보·핫패스 보호
- **스타일**: 매직넘버, 네이밍, 라인 길이, 죽은 코드, TODO/FIXME 잔존
- **주석 부피**: 3줄 이상 주석 블록 / 세션 번호·날짜·결정 id 가 박힌 주석 / 구분선 주석 /
  코드·문서·위키에 같은 설명이 중복된 자리 (`coding/_common.md` *주석 — 기본 1줄*)
- **세션 로그**: `SESSION_LOG.md` 에 40자를 넘는 행이 있는가 (넘치면 커밋·Vault 로 옮길 것을 제안)
- **외과성**: 변경이 요청 범위에 한정되는가(리뷰가 PR diff 대상일 때)

## 출력 형식
심각도별로 분류해 제시한다. 파일:라인 + 근거 규칙 + 제안을 함께.
```
## 요약 (범위 / 점검 파일 수 / 핵심 발견 3줄)

### 🔴 Critical (동작·신뢰성 위협)
- path:line — 무엇이 문제 / 근거(rule) / 제안

### 🟡 Major (규칙 위반, 유지보수성)
- ...

### 🟢 Minor (스타일·개선 제안)
- ...

### 👍 Good (잘 된 점 — 유지 권장)
- ...
```

## 원칙
- **읽기 전용.** 리뷰는 수정하지 않는다. 수정이 필요하면 "수정 prompt 생성" 여부를 사용자에게 묻고,
  승인 시 `prompts/_TEMPLATE.md` 형식의 세션 prompt로 변환한다.
- 칭찬과 지적을 함께(잘 된 패턴은 유지하도록 명시).
- 반복적으로 발견되는 문제 유형은 `wiki-update`로 트러블슈팅/스택 인사이트화할지 제안한다.
