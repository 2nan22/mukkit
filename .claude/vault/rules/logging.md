# logging.md — logging 설정 규칙

## 기본 원칙
- **서비스 코드에서 `print()` 절대 금지.** 모든 출력은 `logging` 을 통한다.
  일회성 측정·조사 도구(`bench/`·`scripts/`·`lab/`)는 예외 — 사람이 그 자리에서 읽는 출력이다.
- **설정은 한 곳에서 한 번, 애플리케이션 진입점에서만.** 파일 위치는 프로젝트마다 다르다 —
  규칙은 *어디에 두느냐* 가 아니라 **한 곳뿐인가**다.
  - 라이브러리·모듈·서비스 코드에서 `basicConfig` 를 부르지 않는다. 먼저 부른 쪽이 설정을 선점한다.
  - `force=True` 를 쓰지 않는다 — 다른 곳의 설정을 말없이 갈아엎고, 테스트 로그를 오염시킨다.
- 각 모듈에서 `logger = logging.getLogger(__name__)` 사용.

---

## 파일 핸들러
```python
TimedRotatingFileHandler(
    filename="〈〈data/out/logs/app.log〉〉",
    when="midnight",
    backupCount=100,
    encoding="utf-8",
)
```
- 자정 로테이션, `backupCount=100`, suffix `app.log.YYYY-MM-DD`.
- Docker 환경에서는 stdout 핸들러 병행(`docker compose logs` 추적).

## 잡 단위 로그 (해당 시)
날짜 파일 하나만 두면 **동시에 도는 다른 잡과 API 요청이 섞여** 사후에 "그 잡만" 읽을 수 없다.
잡 하나가 여러 단계·수십 분을 도는 서비스는 **날짜 로그와 잡 로그를 함께** 둔다.

```
<log_dir>/app.log                     ← 날짜 로테이션. 전체 흐름·기동·API 의 진실
<log_dir>/jobs/<일자>/<job_id>.log     ← 그 잡만. 사후 추적용
```
- **둘 중 하나만 두지 않는다.** 잡 파일은 사후 추적용이고, 무엇이 언제 떴는지는 날짜 파일이 답한다.
- **일자 폴더로 갈리므로 로테이션 대상이 아니다.** 자정을 넘긴 잡은 **시작 일자 폴더에 그대로** 둔다 —
  한 잡이 두 폴더로 갈리면 읽을 때 이어 붙여야 한다.
- **잡 식별은 컨텍스트로 흘린다**(`ContextVar` 등). 한 프로세스에 API 와 잡 처리가 함께 있으면
  루트에 파일 핸들러를 그냥 달았을 때 **남의 로그가 잡 파일에 섞인다.** 비동기 태스크는 생성 시
  컨텍스트를 복사하므로 그 태스크와 하위 태스크에만 보인다.
- **핸들을 닫는다.** 잡마다 열고 종료 시점에 닫는다 — 안 닫으면 잡이 쌓일수록 파일 핸들이 누수한다.
- **로그를 못 쓰는 것이 잡을 죽일 이유는 되지 않는다.** 디렉터리 생성·쓰기 실패는 삼키고 진행한다
  (이 한 가지는 예외다 — 로그는 산출물이 아니다).
- **보존 기간을 따로 정한다.** 잡 로그는 개수가 잡 수에 비례한다 — 날짜 로그와 같은 기준으로 두면
  디스크가 먼저 찬다.

## 로그 포맷
```
%(asctime)s [%(levelname)s] %(name)s — %(message)s
```
JSON 구조화 로그가 필요하면(수집 파이프라인 연동) `python-json-logger`. 초기엔 평문 우선.

## 로그 레벨 가이드라인
| 레벨 | 사용 상황 | 예시 |
|------|-----------|------|
| DEBUG | 핫패스 상세, raw 메타 | 청크 샘플 수, 윈도우 버퍼 길이 |
| INFO | 단계 시작/완료, 라이프사이클 | `chunk #12 done`, `source connected` |
| WARNING | 예상 가능 이상, 폴백 | 재시도 발생, 입력 이상치 |
| ERROR | 예외/외부 호출 실패 | 추론 실패(단위 skip), 파이프 끊김 |
| CRITICAL | 시스템 전체 영향 | 모델 로드 실패, startup 실패 |

기본 레벨 `INFO`. 디버깅 시 `LOG_LEVEL=DEBUG` env로 일시 상향.

## 단계별 구조화 로깅 표준 (핵심)
처리 단위마다 측정 메타를 구조화해 남긴다. 벤치마크와 **같은 키**를 써서 회귀를 추적할 수 있게 한다.

> **⚠️ `extra=` 는 포매터가 부르지 않으면 조용히 사라진다.** 열한 개 항목을 실어도 포맷 문자열이
> 그 키를 안 쓰면 **오류 없이 전부 버려진다** — 그래서 아무도 모른다.
> `extra` 를 쓰는 프로젝트는 **그 키를 실제로 내보내는 포매터**(JSON 포매터 또는 키를 명시한
> 포맷 문자열)를 함께 두고, **키 하나가 실제로 출력에 나타나는지 검사로 못박는다**.
```python
logger.info(
    "unit processed",
    extra={
        "stream_id": stream_id,
        "index": idx,
        "infer_ms": inference_ms,
        "rtf": round(rtf, 3),
        "device": device,   # mps | cuda | cpu
        "model": model_id,
    },
)
```

## 서드파티 로거
- **정책은 우리 로거에만 걸리지 않는다.** 외부 라이브러리가 우리 규약 밖으로 본문을 찍는 일이 있다 —
  콘텐츠를 다루는 라이브러리(자막·미디어·HTTP 클라이언트)는 **이름을 지목해 레벨을 올린다**.
- 억제는 **정확한 로거 이름**으로. 접두 일치로 뭉뚱그리면 이름이 비슷한 다른 로거까지 함께 꺼진다.
- 우리가 만들지 않은 로거의 출력도 **우리 책임**이다 — 유출이 나면 원인이 남의 코드여도 우리가 샌 것이다.

## 부피와 중복
- **같은 경고가 폭주하면 빈도부터 줄이지 말고 원인을 본다** — 대개 설정·규칙이 여러 벌이라
  같은 일이 여러 번 도는 것이다. 억제는 원인을 가린다.
- 로그 부피는 **입력 길이가 아니라 처리 단위 수**에 비례하는 경우가 많다. 잡 1건의 로그량을
  한 번 재서 문서에 남긴다 — 보존 기간·디스크 산정의 근거가 된다.
- 메시지는 **개조식**으로 짧게. 로그는 훑는 색인이다.
- **시험은 운영 로그 파일에 쓰지 않는다.** 로그 대상은 환경으로 가른다.

## 실패 사유를 어디까지 적는가
- **전문은 서버 로그에만, 응답에는 종류까지만.** 실패 사유에 버킷 이름·엔드포인트·원격 응답 본문을
  실어 보내면 그것이 곧 정보 노출 통로가 된다.
- 반대로 **로그에는 원인을 판별할 만큼 남긴다** — 응답만 보고 원인을 못 가르는 상황이 되면
  운영이 로그를 열 수밖에 없고, 그때 로그가 비어 있으면 아무것도 못 한다.

## 민감 정보 / 핫패스 보호
- raw 바이너리(오디오/이미지)는 DEBUG에서도 **길이만**, 본문 dump 금지.
- 방송 콘텐츠 텍스트는 운영 로그 과다 노출 금지(INFO는 카운트만, 본문은 DEBUG 한정).
- 핫패스(per-frame/per-word) 로그는 DEBUG로 격리해 INFO 폭주 방지.
- API 키/토큰/비밀 경로 출력 금지.
